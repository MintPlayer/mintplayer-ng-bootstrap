Datatable

Server-side paginated table with sortable headers, optional virtual scrolling, and single / multiple row selection. Columns are data (DatatableColumnDef[]); the table is fetch-driven — provide a DatatableFetch callback that resolves { data, totalRecords }, and the table handles paging UI, sort state, and (optionally) the virtual viewport. A *bsDatatableRow template renders a row's cells.

Styling — this component renders in the light DOM

It has no shadow root. Anything you render into it — row templates, node templates, cell renderers — stays in the document, so your app's stylesheet, your own component styles and Bootstrap's utility classes reach it normally.

Its own CSS is scoped at build time onto a data-mps attribute, the same device Angular uses for _ngcontent, so it cannot leak out onto your markup.

The trade-off runs the other way: page CSS now reaches this component's internals, exactly as emulated encapsulation behaves everywhere else. ::part() and ::slotted() no longer address it — use ordinary CSS selectors instead.

Row selection

Two selection styles. In the default multiple mode a row click selects (Ctrl+click toggles, Shift+click selects a range) and then emits (rowclick), which is what the Basic usage table above does. In checkbox mode, below, a row click only opens the row: selecting happens in the checkbox cell alone, anywhere inside it.

The selection is keyed by [rowKey], so it survives paging, sorting and reload(): tick rows here, move to another page, sort, and the count keeps every key. With [fetch] that key must be stable, taken from the row itself and never from its position. [rowLabel] names each row checkbox for assistive technology ("Select Coldplay").

Column filters

Mark a column filterable and the table grows a second header row with a dropdown trigger in that column. Columns without it get an empty, correctly-sized cell, so the row stays aligned. No filterable column, no second row at all — toggle the checkbox below to watch the row appear and disappear.

A filterable column gets a built-in panel for free: a search box, an include/exclude toggle, a checkbox list of the column's distinct values, and a clear button. It lives in the shared core, so React and Vue get the same panel with no code of their own. The Name column below uses it as-is, with its values listed by the server ([distincts]).

A checkbox list is the wrong question for a quantity, so a column can ask a different one: filterMode: 'comparison' renders an operator (=, ≠, <, ≤, >, ≥) and a single input, with filterInputType choosing number (the default), date (a calendar day) or datetime (typed in local time, sent as a UTC instant) — the Created column below. Still the built-in panel: no template and no styling of your own. Narrow the operator list with filterOperators when only some make sense.

Quantities only — there is no text input type and no contains operator. Comparing strings is either exact match, which the value list already does better, or a lexicographic >, which is almost never what anyone means. A free-text filter is a nest-your-own case, below.

The consumer picks the mode per column and the component never infers it: a numeric column is often an enum and a string column is often ordinal, so any guess would be wrong about half the time.

When neither built-in question fits, set filterMode: 'custom' on the column and render the panel in a *bsDatatableFilter template — the Country column does. The template receives the column and a context with the loaded values and the search, apply and clear commands. That markup is yours, so you style it yourself: Bootstrap's .form-control is only styled inside bs-* components in this workspace.

The panel is a native popover in the top layer, so it is not clipped by the table's scroll container and is not hidden behind the sticky header — this demo runs in virtual-scroll mode, where both would otherwise happen.

Filtering happens on the server. The table keeps the active filters in a two-way [(filters)] model and sends them, with your own [fetchParams], in every fetch and distincts request; it never filters rows itself. With stateKey, the server render fetches the first page (filters included) and hands it to the browser, so the table hydrates with rows and fetches nothing — view this page with JavaScript off to see it.

Because the browser skips fetch for that first page, anything else your fetch reads off its response (the columns a server query decides, say) belongs in the response's extra, which must be JSON. (pageload) hands it back for every page the table applies, with seeded: true for the page that came from the server. Record it in fetch too: (pageload) fires in the browser only.

Keyboard: Tab reaches each filter trigger; Enter or Space opens the panel and moves focus to its search box; Tab cycles within the open panel; Esc closes it and returns focus to the trigger. Clearing a filter moves focus back to the search box, because the clear button disables itself.

Keyboard, rows — default (multiple) mode:
  • ↑ / ↓ move between rows.
  • Enter or Space selects the row, then opens it (rowClick) — exactly like a click.
  • Ctrl+Space toggles the row and Shift+Space selects a range, the same modifiers as Ctrl+click and Shift+click.
  • → / ← expand / collapse a tree row.
  • Tab reaches each row checkbox; Space on it toggles that row.
Keyboard, rows — checkbox mode:
  • ↑ / ↓ move between rows.
  • Enter opens the row (rowClick) and never selects it.
  • Space toggles the row's checkbox and does not open it. There are no ranges.
  • → / ← expand / collapse a tree row.
  • A click anywhere in the checkbox cell toggles the row; a click elsewhere only opens it.
