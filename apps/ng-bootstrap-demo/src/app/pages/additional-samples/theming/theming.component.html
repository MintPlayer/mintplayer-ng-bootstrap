Theming & dark mode

Bootstrap 5.3 ships a color-mode system based on the data-bs-theme attribute. @mintplayer/ng-bootstrap adds what it leaves out: the user's choice is kept in a cookie, a tiny pre-boot script applies it before the first paint, the server renders it into the HTML, and a toggle and a signal-based service change it.

Three steps, all in your app shell.
  • Add the head tags: the colour-scheme metas, the optional default-mode meta and the pre-boot script.
  • Copy the pre-boot script with an assets glob, and turn off critical-CSS inlining.
  • Drop a <bs-theme-toggle> into your navbar. Server rendering needs no code.

Head tags

The pre-boot script sets <html data-bs-theme> synchronously from the {{ cookieName }} cookie, the site default or prefers-color-scheme, before the browser has resolved any CSS. That is what keeps a dark user from seeing a light flash on reload, on prerendered and cached pages as well as on server-rendered ones. Place it in <head>, after the {{ metaName }} meta it reads and before every stylesheet. It is a plain blocking script on purpose: do not add async, defer or type="module".

<meta name="color-scheme" content="light dark"> lets the browser draw native controls and scrollbars in either scheme. The two theme-color metas colour the browser's own chrome (the mobile address bar, the installed-app title bar) to match the OS scheme.

Copying the pre-boot script

The script ships once, from @mintplayer/web-components/theming/bs-theme-preboot.js: there is no copy in @mintplayer/ng-bootstrap. It is generated from the same cookie and resolve helpers the library uses, so it cannot drift from them, and it stays under 1 KB. Copy it into your build output with an assets glob, so it is served at /theming/bs-theme-preboot.js.

Its file name carries no content hash, so do not serve it with a long max-age: a cached copy would outlive a library upgrade. This demo's server.ts serves it with max-age=0.

Turn off critical-CSS inlining

In a production build Angular inlines the CSS it judges critical for the static index.html and loads the rest asynchronously. That file has no data-bs-theme attribute, so the inliner prunes every [data-bs-theme=dark] rule, and a dark user paints light until the async stylesheet arrives. Angular's CSS minifier strips the comments that would keep those rules, so the fix is to switch the inliner off.

The theme toggle

<bs-theme-toggle> is a single button that cycles through its modes. Its accessible name is the next action ("Switch to dark theme"), its description is the current mode ("Light theme"), and each click is announced to screen readers. All the toggles on this page drive the same document theme, so clicking one updates the others.

With no inputs the toggle cycles auto, light, dark (BS_THEME_DEFAULT_MODES). It talks to the theme store directly, so there is nothing to wire up, and BsThemeService follows every click.

Localized

[modes] is the cycle, in order. Each entry has a mode, a label (the name while it is next), an announcement (the description while it is current) and an icon. To translate the toggle, spread the defaults and override the two strings, so the modes and icons stay the library's.

More modes

Add an entry per custom variant. icon is SVG path data for a 16×16 viewBox (a string, or an array of strings for several paths). Entries whose mode is not a valid mode are dropped with a warning. If the current mode is not in the list, the toggle shows the first entry and moves to the second.

More than three modes? Consider a menu. A cycling button makes the user click through every mode to reach the one they want, and they cannot see the choices up front. Past about three modes, a menu or radio group that calls BsThemeService.setMode() serves them better.

Switching mode from code

BsThemeService exposes the mode as signals. auto resolves to light or dark via prefers-color-scheme and follows the OS live; explicit and custom modes stick. A change in one tab re-themes your other open tabs.

The cookie

The choice lives in a first-party cookie rather than in localStorage, because the server has to see it to render the right theme. The pre-boot script, the store and the server all read the same cookie. With the mode you have now, it reads:

{{ cookieExample() }}

Attribute Value Name{{ cookieName }} (BS_THEME_COOKIE_NAME) Path/ SameSiteLax Max-AgeOne year, renewed on every change SecureOnly when the page is served over https: DomainOnly when you pass cookieDomain (below) HttpOnlyNo: the pre-boot script and the store read it in the page

A value must be 1 to 32 characters of a-z, 0-9 and -; it is matched case-insensitively and lower-cased on read. Anything else counts as no cookie at all. This is a security rule, not a style rule: the server writes the value into the HTML, so the check is what keeps a crafted cookie from injecting markup. isValidThemeMode() implements it.

To share one choice across subdomains, set the cookie's Domain with provideBsTheme(). The value is passed through exactly as given.

The default mode

A site that should start dark declares it once, in the HTML, with <meta name="{{ metaName }}" content="dark"> before the pre-boot script. The script, the store and the Angular server all read the same tag, so there is no provider option to keep in sync. An absent or invalid value means auto. The mode is resolved in this order:

  1. A valid {{ cookieName }} cookie, including auto: a user who chose to follow the OS keeps following it on a dark-by-default site.
  2. The {{ metaName }} meta.
  3. auto.

Server-side rendering

With Angular SSR there is no server code to write. On the server, BsThemeService reads the request's cookie and the page's default-mode meta, and renders <html data-bs-theme="dark"> for an explicit mode, so the first byte of HTML is already themed. For auto it renders no attribute, and the pre-boot script resolves it in the browser. Prerendered pages have no request, so they are themed by the pre-boot script too.

The service does this in its constructor, so it has to exist on every request. provideBsTheme() constructs it eagerly, and so does <bs-theme-toggle>. Add the provider so that pages without a toggle are covered as well:

Send Vary: Cookie with rendered HTML. The HTML now differs per cookie. Without the header, a CDN or reverse proxy that caches the page serves one user's theme to everyone.

Custom variants beyond light & dark

The mode string is open-ended. Author a [data-bs-theme="..."] block in your global styles, then activate it with a toggle entry or setMode('your-variant'). The sepia variant used on this page lives in the demo's styles.scss; try it with the four-mode toggle above or the Sepia button.

Every custom variant must declare --mp-color-mode. Set it to light or dark. The library's web components cannot see Bootstrap's [data-bs-theme=dark] rules through their encapsulation, so they read this token to pick their light or dark icons (the select caret, the switch knob). Without it they fall back to light. auto only resolves to light or dark. prefers-color-scheme doesn't know about custom variants, so they must be set explicitly. Switching to auto while the user is on a custom variant returns them to the system preference.

Build-time customization (SCSS)

Bootstrap's design tokens are SCSS variables. Override them before importing the library's SCSS bundle to bake your palette into the compiled CSS, with no runtime cost. This is the right approach when your brand colors are fixed.

All standard Bootstrap variables ($primary, $body-bg, $navbar-padding-y, …) are available. See the Bootstrap Sass reference for the full list.

Runtime customization (CSS variables)

Bootstrap also exposes most tokens as --bs-* CSS custom properties. Mutating them at runtime lets you build features like a per-user theme picker without re-deploying. The components pick up the change on the next paint.

Note about .btn-primary and .btn-outline-primary. Vanilla Bootstrap 5.3 bakes literal color values into each button variant's scoped --bs-btn-* variables, so mutating --bs-primary at runtime does not reach buttons in a stock Bootstrap project. @mintplayer/ng-bootstrap ships a small override that re-binds .btn-primary and .btn-outline-primary to var(--bs-primary) (with color-mix() for hover / active shades), which is why the buttons above swap with the rest. If you want the same behavior for .btn-success, .btn-danger, etc., add an analogous block in your own stylesheet.

Adaptive navbar

To make <bs-navbar> follow the page theme automatically, pass [color]="'body-tertiary'". The navbar emits bg-body-tertiary (no data-bs-theme override) and Bootstrap's --bs-tertiary-bg CSS variable swaps with the page theme, giving a slightly tinted, theme-aware navbar in both light and dark.

[color] accepts either a Color enum value (Color.dark, Color.primary, …) or a string utility-class suffix ('body-tertiary', 'body-secondary'). Enum values also pin the navbar's own theme via data-bs-theme; string suffixes let the page theme cascade through. null emits no background: a fully transparent navbar that inherits everything from the page.
